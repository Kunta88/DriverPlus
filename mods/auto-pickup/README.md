# Automatic arrival and passenger pickup

`bash mods/auto-pickup/build.sh` runs JVM scenario tests, compiles the production Java helpers and generates their smali under `vek_decoded/smali/com/txdriver/order/`. Only AutoPickup, ArrivalGate and DepartureGate production classes are passed to D8. The Android/application doubles in `test/` must never be packaged in the APK. The script uses the currently installed Homebrew Android tools.

App.onCreate starts one main-looper worker. OrderActivity.updateButtons binds the arrival button through a weak reference. The worker checks the current database order every second; it continues across Activity navigation while the application process is running.

For a PERFORMING order, automatic arrival requires a pickup address, a location fix no older than 30 seconds, and distance within the fleet's arrived-state radius. If the fleet leaves its radius unrestricted, automation uses 100 metres. The original OrderHelper check is also required. Yandex/Uber/Gett orders retain their external-app workflow.

The worker sends the existing OrderStatePacket(state=3), bypassing the manual confirmation dialog for this requested automatic action. It never fabricates a local server acknowledgement. Once the database status becomes ARRIVED, a five-minute countdown begins on the original arrival button. The right-side manual passenger pickup action remains available.

The deadline is stored separately for each server order ID and database row ID. Monotonic time drives the countdown; the saved wall-clock deadline supports process/device restarts. Navigation does not restart the countdown. An ARRIVED order first encountered without a saved deadline receives a new five-minute countdown.

At expiry the worker sends OrderStatePacket(state=4), respecting the existing optional pickup distance restriction. The existing OrderStateHandler starts the taximeter after server acknowledgement, subject to the original tariff/taximeter settings. Offline sends wait for reconnection. Unacknowledged state requests are rate limited to once every 30 seconds. ON_ROUTE/completed/canceled orders stop the wait, and another order cannot inherit it.

Since version 268, an ARRIVED order can also request state=4 before expiry when the vehicle leaves the pickup point. This works after either manual or automatic arrival, while the existing automatic-arrival/pickup option is enabled. Distance is straight-line displacement from the order's pickup coordinates, not accumulated trip distance. Two distinct fixes sustained for at least two seconds must each have distance minus reported accuracy >= 200 metres. Accuracy must be known and <= 50 metres; fixes must be <= 30 seconds old, not in the future, and not predate the current arrival countdown. Invalid/missing pickup coordinates or fixes reset confirmation. Order changes, cancellation, departure from ARRIVED and disabling automation also reset it.

The departure branch deliberately does not apply the optional near-client passenger-pickup restriction: the requested action occurs outside that radius. The existing five-minute branch keeps its original restriction. Both branches share the same rate-limited state=4 request; neither locally marks the passenger picked up or directly starts a meter. Server acknowledgement clears the wait, preventing a later timer-triggered duplicate. A connection loss defers sending; current valid departure evidence or timer eligibility is re-evaluated on reconnect. GPS accuracy checks reduce accidental triggers but cannot establish passenger presence or eliminate all GPS errors.

The JVM tests cover distance limits, missing/stale GPS, offline arrival and expiry, server confirmation before countdown, screen/process recreation, exact timeout boundaries, duplicate suppression, cancellation, order replacement, third-party sources, missing pickup coordinates, and the optional pickup-distance restriction. These tests use doubles and do not replace Android-device or fleet-server testing. A suspended/killed process cannot perform network work until Android resumes/restarts it.

Version 270 adds DwellGate to the production classes packaged by build.sh. The early departure path now requires fifteen continuous seconds inside the arrival zone AFTER the ARRIVED status is observed. Distinct accurate fix timestamps establish the duration; duplicate fixes cannot advance it. Fixes must be at most ten seconds old, gaps over ten seconds reset partial dwell, and the accuracy envelope must fit inside the fleet radius (100 m fallback). Leaving before qualification resets partial dwell. Once qualified, the flag persists only with the current order's saved deadline, surviving activity/process/device recreation. Replacing/canceling the order or disabling automation clears the flag. Old orders without a saved qualification must qualify anew. The original five-minute timeout path is unchanged and does not require this new flag.
